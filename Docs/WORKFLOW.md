# 工作流（WORKFLOW）

> 本文件记录本项目的 Git 使用约定。
> 目的：改动可回滚、历史可读、协作时不互相踩。

---

## 1. 提交与推送节奏

| 动作 | 时机 |
|---|---|
| **提交（commit）** | 功能/修复确认可用之后，且经你确认 |
| **推送（push）** | 提交后经你确认再推 |
| **提醒** | 每完成一个阶段，AI 主动问「要提交推送吗」 |

规则：

- **不自动提交、不自动推送**
- 调参类微调（靶距、亮度、速度）**攒 2–5 次合并**成一次提交，不单独占一条历史
- 临时试验（试完就删）不提交

判断标准：

> **"这次改动如果坏了，我想不想单独回滚它？"**
> 想 → 单独提交；不想 → 攒着合并。

---

## 2. 什么算"一个提交"

一次提交只做一件逻辑上独立的事：

| 可以 | 不可以 |
|---|---|
| 一个功能（拾取系统） | 功能 + 调参 + 改文档 混在一起 |
| 一个 bug 修复 | |
| 一次结构调整（相机重构、预制体化） | |
| 一组相关的参数微调 | |

---

## 3. 提交信息格式

```
<类型>: <做了什么>
```

| 类型 | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `refactor` | 不改行为的结构调整 |
| `docs` | 文档 |
| `chore` | 杂务（配置、依赖、清理） |
| `test` | 测试 |

示例：

```
feat: 军火库白盒场景生成器 + 可复用玩家工厂
fix: 第三人称射线忽略自身，修复自伤与打空
refactor: 玩家改为预制体主路径
docs: 补充游戏愿景文档与 MVP 检查清单
chore: 版本控制模式改为 Visible Meta Files
```

写法要求：

- 一行说清"做了什么"，不写"更新""修改一下"
- 一次提交只描述一件事
- 中文可以，保持前后一致

## 5. 常用命令

```powershell
cd D:\un\demo\1

git status                 # 看当前状态（每次提交前必做）
git diff                   # 看具体改了哪几行
git add <文件>              # 暂存指定文件
git add -A                 # 暂存全部（慎用）
git commit -m "类型: 说明"   # 提交
git push                   # 推送
git log --oneline -5       # 看最近 5 条历史
```

## 6. 网络

`git push` 需要能访问 GitHub。若使用代理：


1. Clash Verge 是否在运行（托盘图标、`verge-mihomo` 进程）

## 7. 撤销与回滚

| 情况 | 命令 |
|---|---|
| `add` 错了，撤回暂存 | `git restore --staged <文件>` |
| 改了想丢弃（不可恢复） | `git restore <文件>` |
| commit 信息写错、还没 push | `git commit --amend -m "新信息"` |
| 撤销最后一次提交、保留改动 | `git reset --soft HEAD~1` |
| 撤销已推送的某次提交 | `git revert <commit>` |

## 8. 分支策略

当前单人开发，**只在 `main` 上工作**。

出现以下情况再开分支：

- 多人协作（每人一个 feature 分支）
- 做破坏性试验（`experiment/xxx`）
- 准备发版（`release/x.y`）

---

## 9. 与 Unity 相关的注意事项

- 场景/预制体是 YAML，多人同时改同一个文件容易冲突 → 约定"一人负责一个场景"
- 跑菜单生成器（`Tools → Armory`）前先 `Ctrl+S`，它会切换场景
- 生成的场景/预制体**不要手动改完又跑生成器**，否则覆盖
- 每次在 Unity 里改完场景记得 `Ctrl+S`，否则 git 里看不到改动
